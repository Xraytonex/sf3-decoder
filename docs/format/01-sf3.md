# Scaffold `.sf3` files

What opensf3 knows about Scaffold's `.sf3` project files. **Everything
here was inferred from public sample files alone** (Scaffold 4.0.5 through
5.3.4, mostly from PRIDE submissions; see `CORPUS.md`). No Scaffold code
was read, decompiled, disassembled, or run. Each claim says how it was
checked. The scripts used for the checks are not part of this repository;
they only read files and never execute anything from them.

Status: **opensf3 reads `.sf3` from Scaffold 4.0-5.3.4**
(`crates/opensf3/src/sf3/`). A file whose contents fail the consistency
checks at the bottom is refused rather than read as a guess.

## Container

- A SQLite database with tables `Files(filename, file BLOB, sha1,
  generation)`, `Version(major, version_name, uuid, generation)`
  (`major` 9 for 4.0-4.4, 11 for 4.11 through 5.3.3), `ProteinGroup(matchProbability,
  peg, msSampleId, id, generation)`, and from 4.11
  `SplitFileIdentifiers(filename, part, uuid)` (empty in our samples).
- Every `Files.file` is gzip-compressed (`1f 8b`). `h.sqlite` inside is
  another SQLite file.
- Inner files come in three kinds: **Java serialization streams** (`ac ed
  00 05`: `Experiment`, the descriptor of every record file, `ModificationTypes`,
  `DatabaseSearch`, ...), **fixed-block record files** (`Name0`, `Name1`, ...),
  and **block-based object files** (`Name<k>`, k from the descriptor).

## Java serialization streams

Standard Java Object Serialization (protocol 2), readable from the public
specification; every stream parses to its last byte in every sample
(field names are in the stream). `Experiment` holds the project:

- `Experiment`: `experimentName`, `programName`, `biologicalSamples`
  (ArrayList), `proteinExperimentGroups`, `hasDecoys`, `parameters`, ...
- `BiologicalSample`: `sampleName`, `category`, `description`,
  `massSpecSamples`.
- `TandemMassSpectrometrySample` (an MS run): `fractionName` (raw file),
  `spectrumCollationId`, `numSpectrumAnalyses`, charge-state counts,
  `hasRetentionTimes`, `proteins`, `proteinGroups` (TIntArrayLists of ids).
- `ProteinExperimentGroup`: `id`, `isDecoy`, `algorithmPreferredAccessionNumber`,
  `accessionNumberSet`, probabilities, `totalSpectrumCounts`. The container's
  `ProteinGroup` table (`peg`, `msSampleId`, `matchProbability`) holds
  Scaffold's protein probability for each group in each MS run (148 groups
  = 148 in 4.0.5).
- `DisplayThresholds`: the peptide and protein probability thresholds and
  minimum peptide count the project was saved with.
- `DatabaseSearch` holds `ProgramDefinition(id, programName,
  programVersion)` (e.g. 3 = Mascot 2.2.04).

## Fixed-block record files

Each record type has a descriptor stream (`PeptideIdentification`, ...) with a
`MathmaticTranslationTable`: `ENTRIES_PER_FILE`, `FILE_SHIFT`, and `files`
(TIntArrayList: part count, then the **index of the last used block** in
each part). Record id -> part file `id >> FILE_SHIFT`, block
`id & (ENTRIES_PER_FILE - 1)`; id 0 is unused, so part 0 holds blocks
1..n and later parts 0..n. Checked: every block's own id (offset 0)
equals its position, in every part of all five samples (621,879
`PeptideIdentification` records over 19 parts in the largest).
`ENTRIES_PER_FILE` is 32768 for most types, 65536 for
`ProteinIdentification`.
Block sizes are fixed per type and **identical in 4.0.5, 4.4.0, 4.11.0**
(checked: part file size = blocks x size, e.g. `PeptideIdentification0` =
32768 x 160):

| type | block | layout (offsets in bytes; LE = little-endian) |
|---|---|---|
| strings (`PeptideSequence`: tails of peptides longer than 30 residues; `SpectrumName`, `StorableProteinName`, `StorableAccessionNumber` (empty in every sample)) | 68 | a string is a chain starting at the block with its id; every block of the chain carries that id, and `next` is a block index **within the same part** (string parts may run past 2^`FILE_SHIFT` blocks to hold continuations; Ctx's part 0 has 134,295): `0` i32 LE record id (same in every block of the record); `4..64` text, padded with `0x02`; `64` i32 LE next block (-1 = end) |
| `Spectrum` | 48 | `0` id; `4` peak-list id; `8` spectrum-name id (title); `12` f64 LE precursor **[M+H]+** (singly protonated mass, not m/z); `20` i32 charge; `32` f32 retention time (s); `36` f32 (TIC or precursor intensity?) |
| `SpectrumAnalysis` | 180 | one per spectrum and search engine: `4` i32 spectrum id; `8` i8 program id (`DatabaseSearch`); `20..164` i32 candidate `PeptideIdentification` ids (0 / `0x7fffffff` = none; not every candidate pointing back is listed) |
| `PeptideIdentification` | 160 | `0` id; `4..34` first 30 residues, padded/terminated `0x0a`; `39`, `40` residues before and after the peptide (ASCII, `?` = unknown); `35` i32 id of the rest of the sequence in `PeptideSequence` (0 = none); `49` f32 peptide probability; `57` i32 spectrum-analysis id; `61` i32 peptide-group id; `66` f32 (Mascot: ion - identity score); `70` f32 Mascot ion score; `74` f32 identity threshold; `78` f32 homology threshold; `82` f32 (delta?); `90`,`94`,`98` i32 modification type ids; `106`,`110`,`114` i32 their positions (0-based residue index); `102` i32 `ModificationTypeIds` list for further modifications, `118` i32 the matching `ModificationLocations` list (0 = none); `122` i32 the `ProteinIdentification` the engine reported; `147` u8 0 = the candidate Scaffold uses for its spectrum, 2 = another candidate or a stale copy; `152` f32 (see *Scores*). Unused slots hold `0x7fffffff`. |
| `ProteinIdentification` | 103 | `0` id; `4` i32 (name id?); `8..31` accession inline, **cut at 22 characters** then `0x0a` (see *Proteins*); `71`,`75`,`79` i32 + `83` an int-list id: ids that are **not** this protein's PSMs (still unknown) |
| `PeptideGroup` | 56 | `32` f32 probability; `36` i32 |
| `SpectrumGroup` | 45 | up to 10 spectrum-analysis ids (packed) |
| `SpectrumIdentificationCache` | 95 | per-engine scores; missing = -3.4e38 |
| int lists (`ModificationLocations`, `ModificationTypeIds`, `PeptidesThatIdentifyProteins`, `ProteinAnalysisIDs`) | 256 | `0` i32 id; then i32 values, ended by `0x80000000` (INT_MIN). `PeptideOverflow` is declared but empty in every sample. |
| `PeakList` | 180 | `0` id; `4..164` 20 (f32 LE intensity, f32 LE m/z) pairs, Scaffold's picks (no isotope peaks among them; unused slots (0, 0), or (-1, -1) in 5.2.2); `164` i32 head of the `PeakListMassIntensities` chain holding the rest (0 = none) |
| `PeakListMassIntensities` | 232 | chained like strings (`next` a block index in the same part; parts run past 2^`FILE_SHIFT` blocks): `0` i32 chain id; `4..228` 28 (intensity, m/z) pairs by falling intensity, NaN after the last; `228` i32 next block (-1 = end) |

### Modifications

`ModificationTypes` (a Java stream) is a whole modification table keyed by
id: `referenceName` (Unimod-style, e.g. `Carbamidomethyl`), `fullName`,
`monoMass`, `averageMass` (f32), `aminoAcidsModified` (residues; lowercase
`n`/`c` = peptide termini), `neutralLossMasses`. Ids are file-specific
(1,541 entries in 4.0.5; more in 4.11). A peptide carries three
modifications inline and the rest in two parallel int lists. In every
sample the two list ids are equal, so which offset names which list
follows the field order (types before positions) and is unconfirmed.

Checked in all five samples: all ~1.3 million modifications sit on a
residue their type allows (0 exceptions). Where two modifications share a
position (Ctx: a cysteine listed with both carbamidomethyl and NEM), the
later one replaces the earlier; that rule fixes all 254 such PSMs' masses.

### Masses

Peptide mass (residues + water + modifications) against the spectrum's
[M+H]+ - proton, best of isotope errors -1..+3:

| sample (engines) | PSMs | <= 10 ppm | <= 50 ppm | worse |
|---|---|---|---|---|
| elife, 4.0.5 (Mascot) | 1,340 | 1,340 | 0 | 0 |
| Ctx, 4.4 (Spectrum Mill, X! Tandem) | 52,711 | 48,322 | 4,355 | 34 |
| MaxQuant demo, 4.11 | 36,622 | 36,622 | 0 | 0 |
| Distiller demo, 4.11 | 55,461 | 38,650 | 16,794 | 17 (< 1000 ppm) |
| Discoverer demo, 4.11 | 621,063 | 334,101 | 286,796 | 166 (< 1000 ppm) |

The 34 Ctx misses are each off by exactly 57.021 Da per unmodified
cysteine: the file says those cysteines are bare, while 84 other PSMs with
a bare cysteine fit unmodified. The file itself is inconsistent there; a reader can only report such PSMs. Peptides with non-standard residues
(X, B, Z) were skipped (<= 846 per file).

### Scores

Each spectrum has one `SpectrumAnalysis` per engine, and several
`PeptideIdentification` candidates point to it (`57`). Offset `147` = 0
marks Scaffold's choice: the candidate with the highest Scaffold peptide
probability (`49`) in 100% of spectra (95% for X! Tandem), **not** the
engine's rank 1. The MaxQuant and Spectrum Mill samples hold every PSM
twice (a copy with `147` = 2 and no peptide group); deduplicate by
sequence and modifications.

Engine scores sit at `66..86` and mean different things per engine.
**Scaffold names them itself**: `Experiment` holds an `AnalysisProgram`
(`programName`, `scoreTypes`) for every engine Scaffold knows, and
`scoreTypes[k]` is the float at `66 + 4k`. Same lists in 5.0.1, 5.2.2
and 5.3.3: Mascot `IonScore - IdentityScore, Ion Score, Identity Score,
Homology Score, Delta Ion Score` (so `66 = 70 - 74`, as measured);
Sequest `Discriminant Score, deltaCn, XCorr, Sp, SpRank, Peak Ratio`;
MSFragger `Discriminant Score, Hyperscore, -Log Expect Value, Nextscore`;
MaxQuant `P-score, Delta score, Percent Ions`; X! Tandem `-Log Expect
Value, Hyper Score, -Log Expect Value, DeltaCN, Ladder Score`; Spectrum
Mill `Discriminant Score, score, percent_scored_peak_intensity, ...`;
"Mascot (Ion Score Only)" (5.3.4) `Ion Score, Ion Score, Identity Score,
Homology Score, Delta Ion Score`, Mascot's layout but for `66`. A "Discriminant Score" is Scaffold's own and is not read as an engine
score. In the
Scaffold 5.2.2 Sequest sample (PXD076594, Proteome Discoverer) `66`
equals `49`, deltaCn runs -0.96..0.99, Sp and Peak Ratio are 0, SpRank
1-10. The ranges below agree with every list except X! Tandem's `70`,
whose ranking contradicts a hyperscore, so X! Tandem stays unnamed.
Other evidence: value ranges, exact identities, and target-vs-decoy AUC
when each spectrum's top candidate by that field is taken (decoy share
in brackets):

| engine | fields | evidence |
|---|---|---|
| Mascot (4.0.5, 4.11 Distiller) | `70` ion score, `74` identity threshold, `78` homology threshold, `66` = `70` - `74` | `66 = 70 - 74` exactly for every PSM in both files; thresholds 25-40; AUC 0.85 (5% decoys) |
| Sequest (4.11 Discoverer) | `74` XCorr (0-7), `78` Sp (1-4440), `82` 1-20 (SpRank), `70` deltaCn, `66` Scaffold's discriminant | Scaffold's list; AUC 0.77 for `74` (16-19% decoys) |
| MaxQuant (4.11) | `66` Andromeda score (6-407), `70` delta score; `78` = `82` = 0 | ranges; AUC 0.94 for `70` (0.3% decoys: already filtered) |
| X! Tandem (4.4) | `66` 0.3-24 (ranked on), `70` 3-98, `74` 0.3-100; names unknown | AUC 0.93 for `66`; `70` ranks targets better when *lower*, so it is no hyperscore |
| Spectrum Mill (4.4) | `70` score (3-27), `74` %SPI (10-100) | ranges; AUC 0.74 (8% decoys) |
| MSFragger (Scaffold Q+S, PXD068782) | `70` hyperscore (5.6-118), `78` next-best hyperscore (<= `70` in 42,598 of 42,600; the rest equal), `74` -log10 expectation (-1.1-100, capped; r = 0.69 with `70`); `66` = `152` = `49` | Scaffold's list, and the ranges agree; the file keeps only matches Scaffold rated >= 0.84 (35 decoys in 21,300 rank-1 PSMs), too few for an AUC |

`152` is Scaffold's discriminant-like score: it equals `66` for Mascot
(Distiller) and MaxQuant and differs elsewhere. `49` is Scaffold's
peptide probability, its output rather than an engine score: opensf3
reports it as such (mzIdentML `MS:1001568`) and never ranks by it.

### Spectrum Mill's lower-case residues

Spectrum Mill sequences write some residues in lower case with no
modification listed: a modified residue. Mass shifts per letter in the 4.4
sample (precursor mass minus the upper-case peptide's): `n` +0.98
(deamidation), `k` +43.01 (carbamylation), `c` +125.05 (NEM), `m` +15.99
(oxidation), each a type the file states elsewhere on that residue. The decoder gives each lower-case residue the one stated type that fits the
precursor mass (24 PSMs fit none or several and are left out).

### Proteins

`BBProteinSequence` (block-based) holds `StorableProteinSequence`:
`id`, `databaseIndex`, `accessionNumber`, `annotation` (FASTA header),
`descriptor`, `proteinAnnotation` (4.11: GO and taxonomy; contains a
`HashSet`), `proteinName`, `sequence`. Only identified proteins are kept.

Each PSM's offset `122` names a `ProteinIdentification` whose accession
matches a stored sequence. In 4.0.5 and 4.4 the peptide occurs in that
sequence for **every** PSM that has one (1,009 and 51,915; I/L treated
alike). **In the three 4.11 demo files it doesn't**: the stored sequences
rarely start with M (454 of 3,448) and contain only 41 of 300 sampled
peptides anywhere, with no consistent offset between records. Either
the demo files ship scrambled sequences or 4.11 stores them differently;
a non-demo 4.11 or 5 file is needed to tell. Until then the decoder
checks peptide-in-sequence and drops (and reports) sequences that fail.

`IdentificationCacheLookup` (a Java stream) maps **every** protein to its
peptide sequences: `proteinAccession`, `proteinID`, `proteinLength`,
`proteinMass`, `sequences`, `cacheLookup` (ids into
`SpectrumIdentificationCache`, a per-peptide best-match cache). This is
the shared-peptide map: in 4.4 and 4.0.5 all 26,567 and 781 listed
peptides occur in their protein's stored sequence; in the MaxQuant demo
none do, so it's the demo's sequences that are wrong, not the map.

Decoys are marked by accession: `-DECOY` suffix in all samples that have
them (the Distiller demo has none).

**The inline accession is cut at 22 characters** (Scaffold 5 Sequest
sample, PRIDE PXD076594: 37,325 records, the terminator never past byte 22,
nothing longer). Older samples never reached 22, so this went unseen until a
UniProt `tr|A0QSM5|A0QSM5_MYCS2` (exactly 22) and its decoy
`tr|A0QSM5|A0QSM5_MYCS2-DECOY` both read `tr|A0QSM5|A0QSM5_MYCS2`: every
decoy PSM then also mapped to its target, so none counted as a decoy (0 of
484,816; the Mascot Scaffold 5 sample, PXD068832, 47 of 15,393 instead of
5,900). `StorableProteinName` (via offset `4`) holds the description, not
the accession. The `IdentificationCacheLookup` map has full names: of the
rank-1 candidates with a 22-character inline name, 63,231 complete to one
accession the map lists for the peptide, almost all to the `-DECOY` form
The decoder therefore:
takes inline names under 22 characters as whole; completes longer ones
from the map (the one listed accession starting with it, else the map's
list alone); completes a name ending in part of `-DECOY` (`..._MYCS2-`,
from a 21-character target) to that decoy; and otherwise leaves the PSM
out, counted. A target whose name fills the field and its decoy read
alike, so those are left out together and the cut stays blind to the
label (Sequest sample: 106,046 matches of all ranks).

Checked so far (4.0.5 sample, Mascot): sequences are valid residues;
`DIPVPKPK`/`DLPVPKPK` (I/L variants) share one spectrum analysis with equal
scores; retention times in `Spectrum` agree with the scan ranges in the
Mascot titles in `SpectrumName`.

## Peaks

A spectrum's peaks are its `PeakList` record's 20 pairs **and** the chain
that record's `164` names, together (sorted by m/z for display). `Spectrum`
`4` names the `PeakList` record; the chain id at `164` is a different
number (record 10402 -> chain 92482 in a 5.3.3 file), so neither file can be
indexed by the spectrum's id. Scaffold keeps at most 300 peaks (20 + 280).
Checked on all 19 sample files: the 20 pairs never
reappear in their chain; every chain block carries its chain's id; and the
b/y ions of Scaffold's >= 95% PSMs (with the decoder's modified peptide for
the same spectrum) fall on the two together more often than on either alone
(within 0.02 Da: detpulldown 59% vs 39% for the 20, Ctx 55% vs 29%,
eLife 55% vs 36%; a +7.3 Da shifted control finds 0-1%). The chains hold the
isotope peaks: b/y + 1.0034 Da (13C) appears there and almost never among the
20, which made a chain read on its own look like y ions shifted by 1 Da.
Reading a chain's `next` as a global id (part x 2^shift + slot) instead of a
slot in its own part sent most chains of parts after the first into other
spectra; that was the first reading and is wrong.

## Block-based object files

Descriptor: `BlockBasedDataFile` -> `BlockBasedSerization` with a class list
(`cm.classPos`, ClassDescs) and `idToLocation` (`file[]`, `location[]`: the
part file `Name<file>` and byte offset of each record). Objects use a
serialization dialect:

- `0x73` object, `0x75` array, `0x70` null, `0x74` string (u16 **LE**
  length, then UTF-8); class reference
  `0x71` + i32 **LE** class id (1-based index into the class list);
- object **fields big-endian**, in descriptor order (superclass first);
- **array lengths and primitive arrays little-endian**;
- classes with `writeObject` write custom data, little-endian, with no end
  marker, so each needs its own reader: `TreeMap` = i32 size, then key and
  value objects; `TIntArrayList` = i32 size, then i32s; `HashSet` = i32
  capacity, f32 load factor, i32 size, then elements.
- A record starts at its location with the object itself (`0x73`) in
  `BBProteinSequence`; in `SpectrumCollation` an i32 id and an i32 come
  first. Look records up by their own `id` field: the position in
  `idToLocation` is off by one.
- `0x7c` is a long string: i64 LE length (a 35,213-residue protein in 4.4).
- `0x7e` is an enum constant: a class reference, then its name as a
  string (`0x74`), as in Java's own `TC_ENUM`. 5.3.3 protein records carry
  GO annotations: `ProteinAnnotation.goAnnotations` is a `HashSet` of
  `GOAnnotation(goboID i32, evidenceType)` with the evidence code as the
  enum (`IMP`, ...); e.g. `00 00 41 f7` = GO:0016887 on an ATP-dependent
  flippase. 53,046 of one file's protein records hold one; earlier files
  had none.
- 4.11 runs sit in `BiologicalSample.msSamples` (a Guava sorted set), not
  `massSpecSamples`; every run links back with `bioSample`. Each run's
  collation lists exactly `numSpectrumAnalyses` analyses in all samples.

`SpectrumCollation` (one per MS run, `TandemMassSpectrometrySample
.spectrumCollationId`) parses to the end in every 4.0.5 record:
`ignoredParentCharges` (i8 per spectrum), `ignoredPlusOneParentMasses`
(f64), a tolerance, and `spectrumGroupIndex` (TreeMap precursor mass ->
TIntArrayList of spectrum-analysis ids). **Run membership:** the ids listed
for a run are exactly the `PeptideIdentification` `57` values of its PSMs
(4.0.5: 17 + 158 + 22 + 317 = 514 spectra, ids 18..1028).

## Consistency checks the decoder makes

- Every block's id matches its position; every string chain terminates.
- Every PSM's peptide mass (with its modifications) matches its spectrum's
  [M+H]+ within 1 Da (isotope errors -1..+3 allowed); PSMs that don't are
  reported and left out (Ctx has 34), and more than 5% refuses the file.
- Every modification sits on a residue (or terminus) its type allows.
- Ranks per spectrum and engine follow the engine's own score (table
  above), never Scaffold's probability; candidates of engines whose score
  fields aren't identified are left out and counted.
- Every peptide occurs in a sequence of a protein it maps to, when the
  sequence is in the file.
- Counts agree with `Experiment`: spectra per run, protein groups vs the
  `ProteinGroup` table.

A file failing any check is refused with the reason; nothing is guessed.

## How the decoder reads a file

`opensf3` opens the SQLite file read-only, inflates the inner files it
needs, and parses the Java streams into plain values (nothing in the file
is ever executed). It reads the runs and their spectra from `Experiment`
and the collations, then every `PeptideIdentification`: sequence,
modifications, the engine's scores, Scaffold's probability and pick. Each
engine's candidates for a spectrum are ranked by that engine's own main
score. Every candidate's peptide mass is checked against its spectrum's
precursor mass (isotope errors allowed). One that misses by more than 1 Da
is left out, and if more than 5% miss, the file is refused as misread. The
same goes for anything structural that doesn't hold, like a block whose id
doesn't match its position or a chain that never ends: the file is refused
rather than half-read. Everything left out is counted and reported.

A few things that aren't obvious:

- Scores sit at `66 + 4k`, where `k` indexes Scaffold's own list of score
  names for that engine. The first entry is often Scaffold's discriminant
  score rather than the engine's. X! Tandem's list doesn't match its values,
  so its scores are named by offset.
- A spectrum's peaks are the 20 pairs in its `PeakList` record plus its whole
  chain. The 20 are Scaffold's picks and the chain holds the rest, isotope
  peaks included. Scaffold keeps at most 300 peaks per spectrum.
- Accessions stored with a candidate are cut at 22 characters, which turns a
  decoy like `tr|A0QSM5|A0QSM5_MYCS2-DECOY` into its target's name. They are
  completed from Scaffold's peptide -> protein map, or by checking whether
  the peptide reads forwards or backwards in the stored target sequence.
- Older files keep a second, stale copy of many candidates; they are counted
  once.
- Spectrum Mill writes modified residues in lower case without saying which
  modification. The one modification the file uses on that residue elsewhere
  that fits the precursor mass is used.
- Scan numbers come from titles that name exactly one scan (`scan=N`,
  DTA-style `name.N.N.z`, Mascot Distiller's `Scan N`); two spectra of one
  run naming the same scan both lose it.
